3. Option 1 - POJO Approach (Main Branch)

Key Metrics

Code per report 40-60 lines
Runtime dependencies 3
Memory overhead ~200 MB
Startup time <1 second
API learning curve ✅ Zero

Strengths

  • ✅ Compile-time type safety - Errors caught by compiler
  • ✅ IDE support - Autocomplete, refactoring
  • ✅ Native Java Streams - No custom API to learn
  • ✅ Minimal dependencies - Only Jackson 
// 1. Define POJO (compile-time type safety)
public class EmployeeReport {
    private Integer employeeId;
    private String firstName;
    private BigDecimal salary;
    // getters/setters
}

// 2. Execute with full type safety
ReportResult<EmployeeReport> result = service.execute("report", params);
List<EmployeeReport> employees = result.getResults(); // Fully typed!

// 3. Transform using native Java Streams API
List<EmployeeReport> highEarners = employees.stream()
    .filter(emp -> emp.getSalary().compareTo(valueOf(80000)) > 0)
    .sorted(Comparator.comparing(EmployeeReport::getSalary).reversed())
    .limit(10)
    .collect(Collectors.toList());

Considerations

  • ⚠️ POJO maintenance - Need to create/update Java class per report (~20-30 lines)
  • ⚠️ Metadata verbosity - Explicit column mappings required
  • ⚠️ Schema changes - Require POJO updates and recompilation

4. Option 2 - Dual Mode (Dataset-impl Branch)

Key Metrics

Code per report 10-15 lines
Runtime dependencies 3
Memory overhead ~220 MB
Startup time <1 second
API learning curve ⚠️ Medium

Custom API Components

  • DataRow - Type-safe wrapper (12 methods)
  • DataSet - Immutable collection (15 methods)
  • DataQuery - Fluent DSL builder (18 methods)
  • DataOperations - Complex ops (11 methods)
  • Total: 56 custom methods to learn/maintain
// NO POJO needed for dynamic mode!

// Execute dynamically
DataSet employees = service.executeDynamic("employees", params);

// Transform with custom fluent DSL
DataSet result = DataQuery.from(employees)
    .filter(row -> row.getBigDecimal("salary").compareTo(valueOf(80000)) > 0)
    .select("name", "salary", "hire_date")
    .orderBy("salary").desc()
    .limit(10)
    .execute();

// Type-safe accessors (no casting)
for (DataRow row : result.getRows()) {
    String name = row.getString("name");              // Type-safe
    BigDecimal salary = row.getBigDecimal("salary");  // No casting
}

Strengths

  • ✅ Dual modes - POJO when needed, Dynamic for flexibility
  • ✅ No POJOs (dynamic mode) - Less boilerplate
  • ✅ Built-in operations - Joins, unions, pivots

Considerations

  • ⚠️ Custom API maintenance - 56 methods across 4 classes
  • ⚠️ Runtime type safety only - Column name typos at runtime
  • ⚠️ Framework lock-in - Proprietary API

5. Option 3 - Spark SQL (Spark-impl Branch)

Important: This uses spark-sql library only for SQL operations in local JVM, NOT distributed Spark cluster.

Key Metrics

Code per report 5-8 lines
Runtime dependencies 4
JAR size ~25 MB
Memory overhead ~400 MB
Startup time 2-3 seconds
Execution mode Local JVM

Strengths

  • ✅ Zero POJOs - No class definitions needed
  • ✅ Auto-inferred schema - No column mappings
  • ✅ Industry-standard API - Widely known
  • ✅ Rich SQL operations - Windows, UDFs 
// Setup Spark (local JVM only, no cluster)
SparkConfig config = SparkConfig.builder()
    .master("local[*]")  // Local execution in Spring Boot JVM
    .build();

// NO POJO, NO column mappings!
SparkReportResult result = service.execute("employees", params);

// Transform using Spark SQL (industry-standard API)
Dataset<Row> summary = result.getDataset()
    .filter("salary > 80000")
    .groupBy("department_id")
    .agg(
        avg("salary").as("avg_salary"),
        max("salary").as("max_salary"),
        count("*").as("employee_count")
    )
    .orderBy(desc("avg_salary"));

// JSON output for REST APIs
String json = result.toJSON();

Considerations

  • ⚠️ SparkSession overhead - ~200 MB memory, 2-3s startup (one-time per app)
  • ⚠️ Additional JAR - +17 MB vs POJO (but still local JVM only)
  • ⚠️ Runtime type safety - Column references via strings

7. Transformation Capabilities Comparison

Operation POJO (Java Streams) Dataset-impl (Custom DSL) Spark-SQL
Filter ✅ stream().filter() ✅ .filter(row -> ...) ✅ .filter("col > val")
Map/Select ✅ stream().map() ✅ .select("col1") ✅ .select("col1")
Sort ✅ sorted(Comparator) ✅ .orderBy("col").desc() ✅ .orderBy(desc("col"))
GroupBy + Agg ⚠️ Manual groupingBy() + reducers ✅ .groupBy().avg() ✅ .groupBy().agg(avg())
Joins ⚠️ Manual Map-based joins ✅ DataOperations.join() ✅ .join(other, "key")
Window Functions ❌ Complex manual code ❌ Not supported ✅ Built-in Window.partitionBy()
Pivot ❌ Very complex ✅ DataOperations.pivot() ✅ .pivot("column")

POJO: Native Java Streams excellent for simple ops, verbose for complex

Dataset-impl: Custom DSL covers common ops, requires maintenance

Spark-SQL: Industry-standard API, richest features, well-documented

Primary Trade-Off

Compile-Time Safety ←────────────→ Development Speed

(POJO with Java Streams)          (Spark-SQL, -87% code)

Dataset-impl (Middle ground, custom API)

Choose POJO if

  • ✅ Compile-time type safety is critical
  • ✅ Team wants native Java Streams
  • ✅ Minimal dependencies required
  • ✅ Willing to accept POJO maintenance

Choose Spark-SQL if

  • ✅ Development speed is priority (87% less code)
  • ✅ Schema changes frequently
  • ✅ Complex analytics needed (pivots, windows)
  • ✅ 17 MB + 256 MB memory acceptable

Choose Dataset-impl if

  • ⚠️ Want both modes (POJO + Dynamic)
  • ⚠️ Willing to maintain custom API (56 methods)
  • ⚠️ Don't need distributed processing
  • ⚠️ Team committed to learning proprietary framework
